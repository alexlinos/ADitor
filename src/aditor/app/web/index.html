ADitor
Active Directory hardening audit

Read-only

This app runs audit reads only. It exposes none of the server's directory-management tools.

Connection

Where to read the directory from, and which account to read it with.

A read-only account is enough

Scanning never writes to Active Directory. It enumerates Group Policy objects over LDAPS and reads their content from SYSVOL over SMB, and that is all. Use a read-only bind account — an ordinary domain user with read access to the Policies container and SYSVOL. It does not need to be, and should not be, a Domain Admin.

Domain controller

Use the name on the controller's certificate. Port 636 is LDAPS; 389 is plain LDAP and will fail a TLS handshake.

Bind account

Its distinguished name, or user@example.com.

Kept in the operating system's credential store. It is never written to ADitor's settings file or to any other file.

Clearing this leaves the LDAPS session encrypted but unauthenticated, so it can be intercepted. The correct fix for a certificate error is to trust the issuing CA on this machine.

Where scans are stored

Each scan gets its own dated sub-folder holding scan.json and report.html. Both contain directory content — Group Policy names, registry values, DNs.

Scan

One read-only pass over the domain's Group Policy, scored against the hardening catalog.

The scan enumerates every Group Policy object, reads its settings from SYSVOL, and compares them with the catalog. It writes one snapshot folder — the JSON payload and the HTML report, both from the same single scan — and changes nothing in the directory.

History

Every scan you have kept. Open a report, or pick two and compare them.

Pick the earlier scan in the first column and the later one in the second. Getting them the wrong way round would turn every regression into an improvement.
